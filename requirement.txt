Build a native macOS Markdown viewer application using Swift and SwiftUI. Application name should be 'MD Viewer'

The product should be designed primarily for **reading and viewing Markdown files**. Editing is a secondary capability and should never dominate the UX or architecture.

## Product Goal

Create a fast, lightweight, native-feeling macOS application for opening and reading Markdown files.

The experience should feel closer to:

- Preview for documents
- VS Code's file/tab persistence
- A lightweight developer utility

rather than a full Markdown IDE or note-taking application.

The main use case is:

1. User opens one or more Markdown files.
2. Files are displayed in tabs.
3. User closes the application.
4. When the application is opened again, the previously opened files and active tab are restored automatically.
5. If an opened Markdown file changes on disk because another application or AI agent modified it, the viewer updates automatically.

The app should be optimized for developers who frequently inspect Markdown generated by tools such as Codex, Claude, GitHub, build scripts, documentation generators, and AI agents.

---

# Core Product Principles

Use these priorities when making implementation decisions:

1. Markdown viewing quality
2. Fast application startup
3. Native macOS experience
4. Reliable file/session restoration
5. Automatic synchronization with files on disk
6. Simple navigation
7. Editing
8. Advanced document-management features

Do not turn the application into:

- a note-taking system
- an Obsidian replacement
- a knowledge base
- an IDE
- a complex Markdown editor

Keep the product focused.

---

# Technology

Use:

- Swift
- SwiftUI
- modern macOS APIs
- structured concurrency where appropriate

Target a reasonably modern macOS version so the implementation does not need excessive backwards-compatibility code.

Prefer native macOS APIs over web technologies whenever practical.

Use AppKit only where SwiftUI does not provide sufficient macOS functionality.

---

# Markdown Rendering

Rendering Markdown correctly is one of the most important parts of the application.

Support at minimum:

- headings
- paragraphs
- bold
- italic
- inline code
- fenced code blocks
- syntax highlighting for code blocks
- ordered lists
- unordered lists
- nested lists
- blockquotes
- links
- images
- horizontal rules
- tables
- task lists
- strikethrough

Support common GitHub-flavored Markdown behavior where practical.

Relative resources must work correctly.

For example:

```markdown
![architecture](./images/architecture.png)
```

should resolve relative to the Markdown document's directory.

Likewise, local Markdown links such as:

```markdown
[Architecture](./ARCHITECTURE.md)
```

should open the referenced Markdown document inside the application.

External HTTP/HTTPS links should open using the system browser.

Prefer a proper Markdown parser producing a structured document/AST instead of implementing Markdown parsing manually.

Investigate Apple's `swift-markdown` package as the initial parsing solution.

Keep the parsing layer separated from the rendering layer.

# Main Window

The main window should have a clean macOS-native layout.

Suggested structure:

```text
┌─────────────────────────────────────────────────────┐
│ Toolbar                                             │
├──────────────┬──────────────────────────────────────┤
│              │ Tab 1 │ Tab 2 │ Tab 3              │
│  Optional    ├──────────────────────────────────────┤
│  Sidebar     │                                      │
│              │          Markdown Content            │
│  Outline     │                                      │
│              │                                      │
└──────────────┴──────────────────────────────────────┘
```

Do not overload the interface.

The Markdown document itself should receive most of the available screen space.

---

# Tabs

Opening files should create document tabs.

Tabs should behave similarly to VS Code or a web browser.

Requirements:

- multiple Markdown files can be open simultaneously
- clicking a tab changes the active document
- tabs can be closed
- tabs can be reordered if practical
- opening an already-open file should activate its existing tab instead of opening a duplicate
- Cmd+W should close the active tab
- Cmd+Shift+[ and Cmd+Shift+] or appropriate macOS shortcuts should switch tabs
- Cmd+O should open a file
- dragging Markdown files onto the application should open them

Track documents using canonical file URLs so the same file is not accidentally opened more than once.

---

# Session Restoration

This is a core feature.

The application must remember the user's working session.

Persist:

- list of open files
- ordering of tabs
- currently active file/tab
- optional scroll position for each document
- window size and position where practical
- sidebar visibility if there is a sidebar

When the application is launched again:

1. restore all previously opened files
2. restore their tab order
3. restore the previously active tab
4. restore scroll position where practical

The experience should feel similar to reopening VS Code.

If a previously opened file no longer exists:

- do not crash
- indicate that the file is unavailable
- allow the user to close the missing tab
- optionally provide a way to locate the moved file

Persist state in an appropriate application-storage mechanism.

Do not store full document contents merely to restore the session.

Store references to files.

Because macOS sandboxing may prevent access to files across launches, properly investigate and implement security-scoped bookmarks if required.

File restoration must work reliably across application restarts.

---

# Recent Files

In addition to restoring the active session, maintain a list of recently opened files.

Provide:

File → Open Recent

The recent-files list should:

- persist between launches
- avoid duplicates
- put most recently accessed files first
- remove files that clearly no longer exist where appropriate
- support clearing the recent-file history

Consider using appropriate native macOS document-controller functionality when possible instead of recreating standard operating-system behavior unnecessarily.

---

# File Watching

This is another important feature.

The viewer should detect when an opened Markdown file changes on disk.

Example workflow:

1. User opens `PLAN.md`.
2. An AI coding agent modifies `PLAN.md`.
3. The viewer notices the change.
4. The rendered document refreshes automatically.

The user should normally not need to press Reload.

Implement file watching using appropriate macOS filesystem APIs.

Avoid aggressive polling.

Debounce rapid sequences of filesystem events so a file written several times during a short operation does not trigger unnecessary rendering.

The architecture should clearly separate:

```text
File watching
↓
Document loading
↓
Markdown parsing
↓
Rendering
```

If the document is currently being edited inside the application, handle external changes carefully to avoid overwriting local edits.

Because viewing is the primary use case, optimize the default behavior for externally modified read-only documents.

# Reader Experience

The Markdown reader should feel polished.

Provide:

- comfortable maximum text width
- good typography
- clear heading hierarchy
- good spacing between elements
- readable code blocks
- horizontal scrolling for very wide code blocks where necessary
- selectable text
- copy support
- dark mode
- light mode
- automatic system appearance

Rendering should feel like a native document rather than a webpage embedded in an application.

Do not use excessive visual decoration.

---

# Outline Sidebar

Provide an optional document outline generated from Markdown headings.

Example:

```markdown
# Project

## Architecture

### Networking

## Installation
```

should produce:

```text
Project
  Architecture
    Networking
  Installation
```

Clicking a heading in the outline should scroll the document to that section.

The outline should update automatically when the document changes.

The sidebar must be optional and easy to hide.

---

# Editing

Editing is secondary.

Do not design the entire application around an editor.

Initial editing support can be minimal.

Possible implementation:

- explicit "Edit" mode
- Markdown source editor
- Save
- Cmd+S
- basic undo/redo

Reading mode should remain the default.

When viewing a document, the UI should not look like a text editor.

Do not spend disproportionate implementation effort building:

- autocomplete
- Markdown formatting toolbars
- WYSIWYG editing
- advanced editor plugins
- code completion
- collaboration

Those are outside the initial scope.

---

# Search

Support document search:

Cmd+F

Searching should:

- find text inside the currently rendered document
- highlight matches
- support next/previous match

Do not initially implement project-wide search.

---

# Supported File Types

Initially support:

- `.md`
- `.markdown`

Potentially allow plain-text Markdown files later.

Register the application with macOS so Markdown files can be opened using:

Finder → Open With → this application

Double-clicking a Markdown file associated with the application should open it in a tab.

---

# Performance

Performance matters.

The application should:

- launch quickly
- open normal Markdown documents essentially immediately
- remain responsive when opening large Markdown files
- avoid reparsing documents unnecessarily
- debounce rapid filesystem changes
- avoid unnecessary SwiftUI view reconstruction

Parsing should occur outside the main UI thread if it could block rendering.

UI updates must happen safely on the appropriate actor/thread.

Avoid premature optimization, but keep large-document behavior in mind.

Use a simple modular architecture.

A reasonable starting structure would be:

```text
App
├── MarkdownViewerApp
├── AppState
└── SessionManager

Document
├── MarkdownDocument
├── DocumentManager
├── FileLoader
├── FileWatcher
├── RecentFilesManager
└── SecurityScopedBookmarkManager

Markdown
├── MarkdownParser
├── MarkdownModel
├── MarkdownRenderer
└── SyntaxHighlighter

UI
├── MainWindow
├── TabBar
├── ReaderView
├── OutlineView
├── CodeBlockView
├── MissingFileView
└── SettingsView

Services
├── LinkHandler
├── ThemeManager
└── SessionPersistence
```

This is guidance, not a rigid requirement.

Prefer understandable code over excessive abstractions.

Avoid unnecessary Clean Architecture ceremony.

# State Model

Design application state around open documents.

Conceptually:

```swift
AppState
    openDocuments: [DocumentSession]
    activeDocumentID: UUID?
```

A document session may contain:

```swift
DocumentSession
    id
    fileURL
    displayName
    parsedDocument
    scrollPosition
    lastKnownModificationDate
    state
```

Possible document states:

```text
loading
ready
missing
error
```

Keep filesystem state separate from rendered Markdown state where practical.

---

# Persistence

Persist session metadata after meaningful changes such as:

- file opened
- file closed
- tabs reordered
- active tab changed
- application terminates

Avoid excessive disk writes.

The application should gracefully recover if stored session metadata becomes invalid or corrupted.

# Drag and Drop

Support dropping Markdown files onto:

- the Dock icon
- application window

Multiple files may be dropped simultaneously.

Ignore unsupported files gracefully.

# Error Handling

Handle these cases gracefully:

- file deleted
- file renamed
- permissions removed
- unsupported encoding
- unreadable file
- invalid Markdown
- image resource missing
- relative link target missing
- persisted bookmark no longer valid

Never crash because an external file disappeared.

Markdown parsing should be tolerant of malformed input.

# Testing

Create tests for important non-UI behavior.

Especially test:

- opening files
- duplicate-file detection
- session serialization/deserialization
- recent-file ordering
- session restoration
- missing files
- relative-link resolution
- relative-image resolution
- file-change handling
- Markdown parsing
- tab ordering

# Development Approach

Implement the application incrementally.

Suggested sequence:

## Phase 1 — Basic Viewer

Implement:

- macOS application
- file picker
- opening `.md`
- Markdown parsing
- Markdown rendering
- basic reader UI

## Phase 2 — Multi-document Sessions

Implement:

- tabs
- document manager
- duplicate-open protection
- active document management

## Phase 3 — Persistence

Implement:

- save open-file session
- restore files on launch
- restore active tab
- recent files
- security-scoped bookmarks if needed

## Phase 4 — Live File Updates

Implement:

- filesystem watcher
- automatic document reload
- debounce
- handling deleted/moved files

## Phase 5 — Reader Features

Implement:

- outline
- heading navigation
- search
- polished code blocks
- relative images
- internal Markdown links

## Phase 6 — Editing

Only after the viewer experience is solid:

- source editing
- save
- undo/redo
- external-edit conflict handling

# Development Rules

While implementing:

- Keep commits logically scoped.
- Do not introduce large dependencies without justification.
- Prefer native macOS APIs.
- Do not implement features outside the defined scope simply because they are common in Markdown editors.
- Do not create abstractions before they are useful.
- Keep rendering, filesystem management, and application state separated.
- Add tests when implementing important state-management behavior.
- Maintain a short `ARCHITECTURE.md` describing important architectural decisions.
- Maintain a `TODO.md` for deferred features rather than implementing them opportunistically.

Whenever there is a design decision between improving the viewer and improving the editor, prioritize the viewer.

---

# Definition of Initial Success

The first meaningful release is successful when I can:

1. Launch the application.
2. Open several Markdown files.
3. Navigate between them using tabs.
4. Close the application.
5. Launch it again.
6. See the same Markdown files restored automatically.
7. See the previously active tab selected.
8. Modify one of those Markdown files using another application or AI coding agent.
9. See the viewer update automatically.
10. Read Markdown with high-quality native rendering.
11. Open local links and images correctly.
12. Search within the current document.

Everything beyond this is secondary.

Build this core experience first before expanding the feature set.
